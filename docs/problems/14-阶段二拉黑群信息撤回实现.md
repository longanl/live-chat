# 阶段二：拉黑、群信息、撤回 + clientMsgId 唯一索引

## 问题现象

阶段一完成后仍缺失：拉黑能力（2.7/2.8/2.9）、群信息修改（3.8）、消息撤回（4.5）、以及 `clientMsgId` 幂等去重。`users` 缺 `signature`、`conversations` 缺 `avatar/notice`，详情与搜索 `relation` 尚无 `BLOCKED`。

## 问题原因

这些功能需要表结构变更（DDL），阶段一刻意回避了 DDL。阶段二统一引入 DDL 并实现。

## 解决方案

### DDL（`chat.sql`）

在 `chat.sql` 的完整 dump 中直接修改 `CREATE TABLE` 语句（源文件），使重新执行即生效；同时在文件末尾追加 `ALTER TABLE IF NOT EXISTS` 语句，对已运行的库也安全（IF NOT EXISTS）。

- `users`：`ADD COLUMN signature VARCHAR(255) DEFAULT NULL AFTER nickname`
- `conversations`：`ADD COLUMN avatar VARCHAR(255)`、`ADD COLUMN notice VARCHAR(500)`
- `chat_messages`：`ADD COLUMN client_msg_id VARCHAR(64) DEFAULT NULL`、`ADD COLUMN recalled TINYINT(1) NOT NULL DEFAULT 0`、`ADD UNIQUE INDEX uk_conv_clientmsg(conversation_id, client_msg_id)`
- 新表 `user_blocks(blocker_id, blocked_id, create_time)`，`UNIQUE(blocker_id, blocked_id)`

**为什么改 `chat.sql` 的 CREATE + 末尾加 ALTER**：`chat.sql` 是该项目的 schema 源文件（无 Flyway/Liquibase），改 CREATE 保证新库一次性到位；末尾 ALTER（IF NOT EXISTS）保证已运行库可独立迁移。

### 拉黑

- `FriendsMapper` 新增 `countBlock`（双向）、`insertBlock`、`deleteBlock`（双向）、`selectBlockedPage`、`countBlocked`
- `FriendsService` 新增 `block`、`unblock`、`blockedList`（分页）
- `block` 校验：不能拉黑自己；`countBlock` 双向查已拉黑则拒绝；`insertBlock(blockerId=当前用户, blockedId=目标)`
- `unblock`：`deleteBlock` 双向删；删 0 行则抛「未拉黑该用户」
- `relation` 判定在 `UserMapper.xml` 的相关子查询中增加 `user_blocks` 双向 exists → `BLOCKED`
- 列表返回 `UserVO`（被拉黑者信息）

**为什么 block 存 `(blocker=caller, blocked=target)` 而不规范化**：被拉黑列表只需 `blocker_id=me` 查询，简单高效；双向判重由 `countBlock` 在写入前完成；取消拉黑由 `deleteBlock` 双向删除。

### 群信息修改

- `MessagesMapper` 新增 `updateConversation(id, name, avatar, notice)`（`<set>` 动态）
- `ConversationService` 新增 `updateGroupInfo`：`requireGroup` + 校验 `ownerId == operatorId`
- `ConversationController` 新增 `PUT /{id}`
- `ConversationVO`、`Conversation` 实体增加 `avatar`、`notice`；`selectMyConversations` SELECT 补充 `c.avatar`、`c.notice`

### 撤回 + clientMsgId

- `MessagesMapper` 新增 `updateRecalled(id, userId)`：`set recalled=1 where id=? and sender_id=? and recalled=0 and send_time > now()-2min`，返回影响行数
- `MessagesService` 新增 `recall`：`updateRecalled` 返回 0 则抛业务异常
- `ChatMessage` 实体增加 `clientMsgId`、`recalled`；`saveMessage` 的 `insertMessage` 加入 `client_msg_id`、`recalled=0`，并用 `try/catch DuplicateKeyException` 处理唯一索引冲突 → `BusinessException("该消息已发送过")`
- `MessagesController` 新增 `POST /{id}/recall`

**为什么用 `try/catch DuplicateKeyException` 而非先查**：先查+再插有并发窗口（TOCTOU），唯一索引是最终保障；catch 保证无论并发如何都返回业务失败。

## 解决了什么问题

阶段二 4 个接口全部可用：拉黑/取消拉黑/拉黑列表、修改群信息、撤回消息；`clientMsgId` 唯一索引生效；`signature/avatar/notice` 列就位。文档已同步 ✅。

限制与遗留：
- 删除消息（4.6）仍待阶段三（需 `message_deletions`）
- `recalled` 字段未返回前端（文档 `MessageVO` 暂无该字段）
- 管理员角色仍不存在，群信息仅群主可操作
- 仅后端，前端对接待确认
