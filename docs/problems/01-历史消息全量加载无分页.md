# 01 · 历史消息全量加载、无分页无过滤

## 问题

后端 `GET /messages/history`（`MessagesMapper.xml` 的 `queryAll`）执行：

```sql
select c.*, u.nickname as nickname, u.avatar as avatar
from chat_messages c join users u on c.sender_id = u.id
order by c.send_time;
```

- **无 WHERE，不分会话**：群聊、所有私聊、全部用户的聊天记录一次性全部返回；
- **无 LIMIT**：消息量线性增长，响应体与后端内存随之线性增长；
- `order by send_time` 无索引命中，每次都对全表做 filesort；
- 前端（`stores/chat.ts` 的 `search()`）把返回的全部消息灌进单个 `history` 数组，
  再在视图层自己过滤群聊（`index.vue`）与私聊（`p2pchat.vue`），内存占用随消息量增长。

## 影响

- 数据量达数万一十几万条时：接口响应变慢、后端内存与网络带宽暴涨、前端渲染卡顿；
- 无法"查看更早的历史消息"，功能随之封死；
- 单条消息的增删改查都耦合"全量重新拉取"的语义。

## 方案：会话（conversation）模型 + 游标分页

1. 引入 `conversations` 与 `conversation_members`，群聊/私聊统一挂到会话下；
2. `chat_messages` 增加 `conversation_id`，全表查询改为按会话过滤；
3. 历史接口改为游标分页：

   ```sql
   select c.*, u.nickname, u.avatar
   from chat_messages c
   join users u on u.id = c.sender_id
   where c.conversation_id = #{conversationId}
     and (#{beforeId} is null or c.id < #{beforeId})
   order by c.id desc
   limit #{limit}   -- 应用层 reverse 回正序
   ```

4. 前端每个会话独立维护消息列表，向上滚动到顶部时用当前最小 `id` 作为
   `beforeId` 继续加载更早的消息；
5. WebSocket 协议保持不变，后端 `resolveConversation(type, senderId, receiverId)`
   解析出 `conversation_id`（群聊用内置群会话，私聊按成员对查找或惰性创建）。

## 落地

- ✅ 数据库：`conversations` / `conversation_members` / `chat_messages`（见 05、06）
- ✅ 后端：`GET /messages/history?conversationId=&beforeId=&limit=`
- ✅ 前端：会话级存储 + 滚动加载（`stores/chat.ts`、`index.vue`、`p2pchat.vue`）
