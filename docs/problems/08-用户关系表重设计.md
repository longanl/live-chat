# 08 · 用户关系表重设计

## 问题

旧 `user_relations` 用**每个方向一条**、共两条对称行表示一段好友关系，
`status` 一列同时承担"方向 + 生命周期状态"：

- `0` = 未确认（收方侧）、`3` = 已发送（发方侧）——都是"待处理"，靠行位置区分；
- `1` = 已添加、`2` = 已拒绝。

### 影响

1. **status 语义过载**：收/发方向没有独立字段，"待处理"到底是发给我的还是我发出去的，
   完全取决于看哪一行，容易读错（如 `listRequest` 的 `user_id=? AND status=0` 反直觉）。
2. **双向两行存储**：`insert / update / delete` 每次都是两条 SQL，靠事务硬撑；
   任何一侧丢失/漂移就静默不一致。
3. **同时互加语义错乱**：A、B 同时互相发送申请时，两条
   `INSERT ... ON DUPLICATE KEY UPDATE status=VALUES(status)` 会互相覆盖 3/0，
   各自的"待处理"进错收件箱，必须靠后续 approve 兜底才恢复。
4. **拒绝无区分**：reject 把两条都置 `2`，无法区分"我拒了别人"还是"我被拒"。
5. **无请求已读/处理标记**：新朋友入口只能以"存在任意 status=0"为凭，无法表达已查看。
6. **索引低效**：`idx_status(status,user_id,friend_id)` 以低基数列开头基本无用，
   真查询靠的是双向复合索引。

## 方案（对标微信，拆分"关系"与"请求"）

把**关系（双向、不可变）**与**请求（单向、有生命周期）**拆成两张表：

```sql
-- 好友关系：每对好友一行，约定 user_id < friend_id（应用层归一化）
CREATE TABLE `friend_relations` (
  id BIGINT (20) NOT NULL AUTO_INCREMENT,
  user_id    BIGINT (20) NOT NULL COMMENT '好友对中较小的一方',
  friend_id  BIGINT (20) NOT NULL COMMENT '好友对中较大的一方',
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_pair (user_id, friend_id),
  KEY idx_friend (friend_id)
) COMMENT='好友关系';

-- 好友申请：单向，表达方向
CREATE TABLE `friend_requests` (
  id BIGINT (20) NOT NULL AUTO_INCREMENT,
  from_user_id BIGINT (20) NOT NULL COMMENT '申请人',
  to_user_id   BIGINT (20) NOT NULL COMMENT '接收人',
  status TINYINT NOT NULL DEFAULT 0 COMMENT '0-待处理 1-已同意 2-已拒绝(可再次申请)',
  handle_time DATETIME DEFAULT NULL,
  create_time DATETIME DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_from_to (from_user_id, to_user_id),
  KEY idx_to_status (to_user_id, status),
  KEY idx_from (from_user_id)
) COMMENT='好友申请';
```

### 语义

- 好友列表 = `friend_relations` JOIN users（原 conversation_id 子查询保持不变）；
- 收到申请 = `friend_requests WHERE to_user_id=? AND status=0`，方向天然明确；
- 互加不再冲突：`uk_from_to` 天然去重，先申请的一方自动转为已同意；
- 同意 = 标记申请为已同意 + 写入 `friend_relations`（同事务）；
- 拒绝 = `status=2`，对方仍可再次申请（重新 upsert 回 0）；
- 删除好友 = 删 `friend_relations` 行 + 作废两人之间待处理的申请，防旧申请冒泡；
- 自加、重复申请、无待处理申请等场景返回业务提示，由全局异常处理转为 `Result.error(msg)`。

## 迁移（旧库）

```sql
-- 1) 已添加的好友：双向 status=1 ⇒ friend_relations 每个用户对一行（归一化）
INSERT IGNORE INTO friend_relations (user_id, friend_id, create_time)
SELECT LEAST(a, b) AS user_id, GREATEST(a, b) AS friend_id, MIN(create_time)
FROM (
    SELECT user_id AS a, friend_id AS b, create_time
    FROM user_relations
    WHERE status = 1
) t
GROUP BY LEAST(a, b), GREATEST(a, b);

-- 2) 待处理请求：status=3(已发送) ⇒ from→to；status=0(未确认) ⇒ to...from 反向归一到 from=发起方
INSERT IGNORE INTO friend_requests (from_user_id, to_user_id, status, create_time)
SELECT from_user_id, to_user_id, 0, create_time FROM (
    SELECT user_id AS from_user_id, friend_id AS to_user_id, create_time
    FROM user_relations WHERE status = 3
) t;

-- 3) 建表后删除旧表
DROP TABLE user_relations;
```

> 新库直接以 `chat.sql` 全量导入即可，不存在上述迁移。
> 回滚：`DROP TABLE friend_relations, friend_requests;` 后从备份恢复 `user_relations`。
