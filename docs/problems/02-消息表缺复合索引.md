# 02 · 消息表缺复合索引，排序走向 filesort

## 问题

旧 `chat_messages` 只有两个单列索引：

```sql
KEY `sender_id` (`sender_id`),
KEY `receiver_id` (`receiver_id`)
```

实际查询却总是成对出现：

- 历史消息：`where ... order by send_time`（全表 filesort，无索引可命中）
- 标记已读：`update ... where sender_id=? and receiver_id=?`
- 未读数：`where sender_id=? and receiver_id=? and read_status=0`

单列索引只能先命中一列，再回表 + 二次过滤 + filesort，无法覆盖以上三类查询。

## 方案

新表结构用 `conversation_id` 替代 `(sender_id, receiver_id)` 的语义，并为其建立
匹配真实查询模式的复合索引：

```sql
KEY `idx_conv_id` (`conversation_id`, `id`)     -- 游标分页：按会话取较新的 id
KEY `idx_sender` (`sender_id`)                  -- 发送者维度（头像/昵称回查等）
```

`conversation_members`：

```sql
UNIQUE KEY `uk_conv_user` (`conversation_id`, `user_id`)  -- 成员唯一 + 未读 upsert 冲突来源
KEY `idx_user` (`user_id`)                                 -- "我的会话"反查
```

`users` 在线状态：

```sql
KEY `idx_status` (`status`)   -- queryOnlineUser / count 打点
```

好友关系表已随 `problems/08` 拆分为 `friend_relations`（`uk_pair`）与 `friend_requests`（`uk_from_to` / `idx_to_status`），
不再是双向两行 + 低基数的 `idx_status` 结构。

## 附带收益

- 未读数查询从"扫用户全部消息"降为"索引 range scan 计数"；
- 排序由 `(conversation_id, id)` 掩盖，翻页深也不会退化；
- 文件消息增加独立列后（见 04），`file_type` 可按需再索引。
